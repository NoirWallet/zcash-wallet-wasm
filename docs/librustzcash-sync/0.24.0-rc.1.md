## Local changes to preserve

### `zcash_client_memory`

The WASM wallet uses the in-memory backend that upstream moved to
`zcash/zcash_client_memory`. The standalone repository still targets
`zcash_client_backend 0.23`, so this project keeps the vendored crate and adapts
it to the 0.24 API.

Project-specific behavior that must remain:

- Protobuf serialization of the complete in-memory wallet.
- Low-peak-memory `encoded_len`, streaming encode, and chunked encode paths.
- Backward-compatible decoding of Orchard note versions.
- Transparent receiver metadata and address lookup fixes.
- Account names, address generation/listing, and conservative UTXO query height.
- Incremental block cache and synchronization support used by the WASM API.

The 0.24 adaptation must add Ironwood received notes, spends, nullifiers,
commitment tree state, balances, and serialization without changing existing
field numbers.

### `zcash_client_backend`

- Keep `sync::run_next_batch`, used by the browser-friendly incremental sync API.
- Keep `sync::refresh_utxos` public, used by the custom sync workflow.

The old local expiry-delta helper is not carried forward. Upstream 0.24 exposes
`create_pczt_from_proposal(..., target_expiry_height, ...)`, which provides the
same capability without a library patch.

### WASM integration

- Keep dynamic ZIP-317 fee APIs and expiry-delta behavior.
- Keep hardware-wallet PCZT redaction and combination APIs.
- Keep branch-aware lazy Orchard proving and verifying key caches.
- Keep Ironwood proof generation and extraction support.
- Keep serialized wallet compatibility for existing persisted browser data.

## Migration preparation APIs

The WASM surface should expose enough policy and state for the host application
to orchestrate migration without implementing consensus logic:

- Per-pool Orchard and Ironwood balances.
- A transfer proposal restricted to legacy Orchard inputs.
- Normal post-NU6.3 transfers routed by `zcash_client_backend` to Ironwood.
- Transaction target/expiry metadata needed by a persisted migration schedule.

Amount selection, user consent, scheduling, background execution, and network
privacy remain host-application responsibilities until an official migration
API is released.

Implemented WASM APIs:

- `get_ironwood_activation_height`
- `pczt_orchard_migration_create`
- `oneclick_pczt_orchard_migration`
- `estimate_orchard_migration_fee`

The migration proposal uses upstream `propose_send_max_transfer` with
`MaxSpendMode::MaxSpendable` and an Orchard-only source pool. It rejects calls
before NU6.3, requires a destination owned by the source account, and records
transaction version V6. At and after NU6.3, the upstream receiver-selection
logic carries the destination's Orchard receiver in the Ironwood bundle. Normal
transfers continue to select V5 or V6 from their target height, so the same WASM
build remains usable on mainnet before activation.

## Verification

- Root WASM `cargo check` passes with the rebuilt nightly standard library.
- `make wasm` passes, including `wasm-bindgen`, O4 optimization, worker-module
  post-processing, and regeneration of the checked-in `pkg` artifacts.
- The memory backend host test suite passes with Orchard and transparent inputs.
- Regression coverage includes Ironwood note/nullifier persistence, legacy V3
  wallet decoding, and Orchard-only send-max routing to Ironwood after NU6.3.
- Excluding the restored `zcash_client_memory` crate, the vendored upstream tree
  differs from commit `54ff6731` only in the workspace member/lockfile and the
  restored custom synchronization APIs.

The project-supported memory-backend configuration enables both `orchard` and
`transparent-inputs`. The standalone crate's `--no-default-features` build is
not supported because existing project-specific account/address APIs depend on
transparent-input functionality even when that feature is disabled.
